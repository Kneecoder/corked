# Corked audit: `corked_v6.html` + `worker.js` (read-only, nothing changed)

Five of these would bite your outside testers early: #1 (anyone with the worker URL can spend your credit), #2 and #3 (answers get lost or passed through without a grade), #4 (a result can land in the wrong bottle), and #9 (the hosted page can't reach the worker at all). The direct answers to your questions 2 and 3 are in #6 and #8.

Everything here comes from reading the code. I didn't run anything, and I didn't retest the three issues you already listed.

---

### 1. Anyone who has the worker URL can spend your API credit. **Confirmed.**
- **What's wrong:** `worker.js:2247-2283` has no auth, no rate limit and no per-user cap. The CORS check at `worker.js:2249-2251` only stops *browsers* on other websites. A script calling the URL directly isn't affected.
- **Why it matters:** The URL isn't secret. Every tester will have it in their browser. Each `/m0` call can use up to 1,600 output tokens (`worker.js:2195`), and `/field` retries once (`worker.js:1843`).
- **Two smaller problems in the same code:**
  - `callClaude` (`worker.js:1200`) has no timeout. When the app gives up after 30s, the worker keeps running and billing, and the user's retry pays twice.
  - Error replies pass Anthropic's raw error text and the model's raw output straight back to the browser (`worker.js:1217`, `1236`).
- **What's safe:** No API key is in the frontend. I searched and found nothing.
- **Fix size:** Small. Set a Cloudflare rate-limit rule, give each tester their own access key and check it in the worker, and set a spend limit in the Anthropic console.

### 2. Coming back to a parked question at M4–M7 loses the answer, or grades it into the wrong bottle. **Confirmed.**
- **What's wrong:** `openBottle` (`corked_v6.html:5414-5416`) only knows three types of parked question: `ask`, `echo` and `find`.
  - **M5** parks as `ask` (`parkM5Gap`, `4071-4076`). It opens the *ask* panel, and `submitDormantAsk` (`5650`) puts the answer in a holding variable. Only M2's Phase A reads that variable (`3686`). At M5 the answer is never graded, and it stays in memory.
  - **The leak:** the next time *any* bottle reaches M2, that stranger's answer gets graded as M2. The echo version is the same: M4's backup brief is labelled `echo` (`4006`), so an M4 answer can get graded as another bottle's M3 (`3130`).
  - **M4, M6 and M7** park as `contrast`, `words` or `limit`. `openBottle` has no route for those, so it falls through to `renderMech`, whose save wipes the brief (`saveBottle`, `2110`). The user gets the plain question back, and the generated brief is gone.
  - On the way back into M5, the panel's backup question falls back to M2's question (`5601`).
  - Cellar cards show "Parked · find the person" for all these types (`5345-5347`).
  - Parking from the label screen also drops the answer, because `renderMech` goes straight to `showLabel` (`3054`). That may overlap your known label issue.
- **Why it matters:** Answers disappear or land in the wrong bottle, with no error shown.
- **Fix size:** Medium. Route by which mechanism parked, not by the brief's type, and clear both holding variables whenever a bottle opens.

### 3. An answer can be stored as "answered" without ever being graded. **Confirmed.**
- **What's wrong:** Every path writes the answer *before* calling the worker: `S.answers[m.id] = txt` (`4243`), plus `3697`, `3958` and `3626`. If the call fails, nothing rolls it back. `restoreAnsweredMechUI` (`4466-4478`) then treats any stored answer as graded and sets `obsShown = true`, so Continue moves on.
  - **Coming back from a park:** `triggerM2PhaseA` and `triggerM3EchoReentry` set the answer during `renderMech`, and `renderMech` saves it (`3203`). If the grade fails, the catch at `3698-3703` / `3959-3963` re-enables the button while `obsShown` is still true. Clicking it (the label still says "Reading answer...") skips the mechanism with no grade. The answer box also stays hidden, and the typed answer is thrown away (`3688`, `3951`).
  - **Normal path:** after a failure, if the user edits their answer, the 800ms autosave (`2946-2949`) stores the ungraded answer. On reopen, it shows as answered.
- **Fix size:** Small. Write the answer only after a successful grade, or save a separate "graded" flag.

### 4. A worker result that arrives late gets written into whichever bottle is open. **Confirmed.**
- **What's wrong:** The `applyM*Result` functions change the shared `S` and then `saveState()` into `activeBottleId`.
- **How it happens:** The sidebar's back-to-cellar button (`1770`) still works while a call is running. `openBottle` swaps in another bottle's `S` and ID (`5402-5405`). A reply that arrives after that grades the *other* bottle.
- **Parking has a similar race:** `parkItAction` (`3918-3935`) shows a timeout error after 30s but lets the park keep running. When it finishes later, it parks the bottle and throws the user back to the cellar. Clicking the button again parks twice.
- **Fix size:** Small. Record the bottle ID when the call starts and throw the result away if it no longer matches.

### 5. Reopening M2 reruns Phase A, even when M2 is already answered. **Confirmed. Whether the wording changes is suspected.**
- **What's wrong:** `renderMech` calls `triggerM2PhaseA()` every time it draws M2 (`3113`). The re-entry case is the only one that skips it.
- **What that causes:** A refresh, or going to the cellar before pressing Continue, does three things:
  - It makes another paid `/m2` call.
  - It overwrites `S.m2_problem` and `S.m2_confirmed_problem` *after* M2 was already graded (`3777-3779`). If the model words the problem differently, M3–M7 are graded against a different problem from M2.
  - It hides the answer box. If the call fails, the button stays disabled for good (`3752-3754`).
- **Fix size:** Small. Skip Phase A when `S.m2_problem` already exists. This doesn't touch any prompt.

### 6. Scheduling (your Q2): the date is set once and never enforced. **Confirmed.**
- **Where it's set:** once, in rhythm setup only:
  ```js
  // corked_v6.html:4416-4425  completeCellarRhythm()
  S.nextQuestionAt = computeNextQuestionAt(S.pace, S.notifTiming);
  ...
  mi = 1; S.mechIndex = mi; saveState(); renderMech();   // M2 shown immediately
  ```
- **What never happens:**
  - Nothing recalculates the date after an answer. The step-2 branch of `p1Next` just does `mi++; renderMech()` (`4295-4298`).
  - Nothing checks the date before showing the next question. The comment at `5352-5356` admits the date is a leftover.
  - For parked questions, `computeParkNextQuestionAt` (`4314`) sets a date, but `dormantIsLocked` is only informational (`2236-2240`).
- **What the user sees:** Cellar cards say "Question in 7 days" while the question is already available. After the date passes, they say "Question ready" and stay that way (`5357-5365`).
- **Two date formulas that disagree:**

  | Function | Uses | Doesn't use |
  |---|---|---|
  | `computeNextQuestionAt` (`4429`) | calendar days + time of day | test mode |
  | `computeParkNextQuestionAt` (`4314`) | now + `PACE_DURATIONS` | time of day |

- **Fix size:** Medium. This is really the paced-returns feature itself.

### 7. The "stalled" and "sagging" timers reset whenever a bottle is opened, not when it's answered. **Confirmed.**
- **What's wrong:** `bottlePaceMultiples` reads `updated_at` (`2176-2184`). `saveBottle` updates `updated_at` on every save (`2109`), and saves happen on:
  - every `renderMech` (`3203`)
  - typing autosave (`2946`)
  - the cellar entry animation (`2962`)
- **Result:** Opening a bottle clears its sag. The acknowledgement logic (`2203-2213`) says "a later touch (new answer)", but in practice any visit counts.
- **Why it matters:** Paced returns and stalls will be built on this timer.
- **Fix size:** Small. Add a separate `lastAnsweredAt` field.

### 8. Data (your Q3): no timestamps on answers, and history is overwritten. **Confirmed.**
- **What a bottle stores:** `{id, created_at, updated_at, status, mechIndex, brief, nextQuestionAt, stallAckAt, stallAckUpdatedAt, s}`. Inside `s`:
  - `answers`: plain strings keyed M1–M7
  - `elements`: state strings
  - `label` and `lastSource`
  - `m0`–`m7`: the latest worker reply only
  - `m2_problem` and `m2_confirmed_problem`
  - `mX_pending_brief`
  - `pace`, `notifTiming`, `qLifecycle`
- **Timestamps:** Only briefs have one (`created_at`). Answers, grades and state changes have none.
- **What gets lost:**
  - Answering again replaces the old answer: `4629-4650` (review reopen), `4825-4845` (label reopen), `3626` (swirl). It also replaces `S.mX`.
  - `rankUp` only ever raises a grade (`3505-3516`). So an element can stay Settled after the answer that earned it has been replaced by a weaker one.
  - `parkBottleDormant` replaces the brief, and `wakeBottle` clears it (`2131`, `2160`).
- **Storage:** Everything lives in one browser's localStorage. There's no copy on a server, so switching device or clearing site data loses the whole cellar.
- **Why it matters:** A dated history view has nothing to show yet.
- **Fix size:** Medium. Add an append-only event list per bottle.

### 9. The hosted version won't be able to reach the worker as configured. **Confirmed.**
- **Origins:** `wrangler.toml` only allows `localhost:8080` and `localhost:5500`. For any other origin, the worker replies with the first allowed origin instead (`worker.js:2251`), so the browser blocks every call. `workerFetch` then reports "Could not reach the worker. Check your connection and Worker URL." (`2002`), which is the wrong explanation.
- **Worker URL:** There's no default URL built in. Testers get a developer field asking them to paste an endpoint (`2595-2601`, `5782-5785`).
- **Fix size:** Small. Add the hosting origin, and put a default worker URL in the frontend.

### 10. A failed swirl follow-up corrupts the stored answer and can't be retried. **Confirmed.**
- **What's wrong:**
  - `submitSwirl` writes the combined answer before the call (`3626`).
  - On failure, the grades still belong to the original answer, while `answers` holds the combined text. The next save keeps that mismatch.
  - `finally` closes the panel (`3656-3660`), and `markSwirlShown` has already set `swirl_done` (`3578`), so the swirl never appears again.
- **Fix size:** Small.

### 11. Length limits can permanently break a bottle. **Confirmed for the problem box; the spark fallback is suspected.**
- **Problem box:** The "Recovered line" input (`1795`) has no `maxlength`. The worker rejects `confirmed_problem` over 500 characters (`PROBLEM_LENGTH_CAP`, checked in `handleEvidenceMechanism`, `worker.js:1934`). So every M3–M7 and `/field` call returns 400, and once confirmed there's no way to edit the problem.
- **Spark fallback (suspected):** `getSparkSummary` falls back to `S.idea` (`3339`), but `/m2` and `/field` cap `user_line` at 300 characters (`worker.js:1707`, `1812`), while M0 allows sparks up to 500.
- **Fix size:** Small. Add `maxlength` attributes.

### 12. Bad or broken replies. **Confirmed.**
- **Non-JSON replies:** In `workerFetch`, `res.json()` runs outside the try block (`2011`). A Cloudflare HTML error page shows the user "Worker error. Unexpected token '<'…". The 30s timer is also cleared before the reply body is read (`2008`).
- **Missing grades:** Missing or unknown states become `turbid` in the worker (`worker.js:1956-1961`) and in the client (`3540`). A broken reply therefore turns into a real Turbid grade that marks the element as answered.
  - ⚠️ Changing that touches grading, so I've stopped there.
- **Wrong error text:** `submitDormantFind` shows "Could not reach the worker" for every error, including 400 validation errors (`5571-5574`).
- **Fix size:** Small, apart from the grading part.

### 13. The same code is copied in many places, which is what caused #2. **Confirmed.**
- **The M2–M7 dispatch chain appears six times:**
  - `3626-3645`
  - `4243-4262`
  - `4624-4652`
  - `4820-4848`
  - `3913-3920`
  - `4860-4866`
- **Other copies:**
  - Two reopen default maps: `REOPEN_DEFAULTS` (`4570`) and `LABEL_REOPEN_DEFAULTS` (`4715`).
  - In the worker, `handleM4` and `handleM6` are hand copies of `handleEvidenceMechanism` (`worker.js:2104`, `2018` vs `1925`).
  - State is stored twice and can disagree: the outer `status` / `nextQuestionAt` / `mechIndex` fields vs `S.qLifecycle` / `S.nextQuestionAt` / `S.mechIndex`.
- **Why it matters:** Each new mechanism or park type has to be added in every copy.
- **Fix size:** Medium. I'm only noting it, since you ruled out restructuring.

### 14. Dead code and leftovers. **Confirmed.**
- **Never called:** `formatNextQuestion` (`4438`) and `showGrapeJudgment` (`3444`).
- **Can't be reached:** `applyLocalMechanismResult` (`3518`, word-count grading). M1 is prefilled and M2–M7 all go to the worker.
- **Never read:** `freshState` fields `progress`, `grapeStep`, `m1Fields`; `grapeStepShown` and `curAssess`; `corked_m0_saved` is written but never read (`6037`).
- **Old migration:** `migrateOldSave` (`2249`) still runs.
- **Test mode:** Anyone can turn on rhythm test mode with `?rhythmtest=1` in the URL (`4308`).
- **Stacked listeners:** `startPhase1` and `openBottle` add another autosave listener every time a bottle opens (`2946`, `5465`). They're harmless because they share one timer.
- **Fix size:** Small.

---

**Performance:** nothing looked slow for five testers. The whole cellar is re-read from localStorage on every save, but that's trivial at this size.

**If I were ordering the fixes:**
1. #1 and #9 before any link goes out.
2. #2, #3 and #4, because they silently lose answers or put them in the wrong bottle.
3. #7 and #8 before you build paced returns and the history view.
